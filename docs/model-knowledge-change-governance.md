# 模型、知识库与变更治理

本文件是 MedPilot 的上线前控制面。它描述的是可审计的工程闸门，不是医疗器械注册、医院信息化验收或临床使用授权。当前系统状态仍为“受控临床试点 / 待医院审批”，在医院伦理、隐私、信息安全、临床科室和信息中心共同签署前，不得用于真实患者分诊。

## 国内来源优先

知识来源先从医院正式发布的本地制度、急诊分诊流程、科室目录和信息系统接口规范开始。外部资料只作为补充，不能覆盖本院制度。建议由医院知识管理员在 `knowledge_source_register` 登记以下证据，并保存原文、版本日期、下载时间和 SHA-256：

| 来源类别 | 首选发布方 | 使用边界 |
| --- | --- | --- |
| 医疗质量安全核心制度、分级诊疗和患者安全 | 国家卫生健康委员会（`nhc.gov.cn`）及省/市卫生健康委 | 作为安全原则和流程映射，不直接生成自动分诊规则 |
| 医疗器械/人工智能软件监管要求 | 国家药品监督管理局（`nmpa.gov.cn`） | 用于产品属性、风险管理和变更记录；需由医院法规/质量部门判定适用性 |
| 个人信息保护、网络安全和数据安全 | 中国政府网（`gov.cn`）、国家网信部门及医院制度 | 用于数据最小化、跨境/第三方服务禁用和留痕要求 |
| 本院制度与业务主数据 | 医院医务处、护理部、急诊科、信息中心、质量管理部门 | 最高优先级；必须有生效日期、适用院区/科室和责任人 |

录入时必须填 `domesticOfficial`、发布方、原始 HTTPS 地址、版本/发布日期、适用范围和校验摘要。系统写入后状态固定为 `PENDING`；只有经过有资质临床审核者复核，才允许将对应文档标记为 `APPROVED`。AI 服务只接收已批准且未过期文档，公开网页不会被后台自动抓取或直接进入 RAG。

## 模型发布闸门

每次发布都必须建立 `model_releases` 记录，至少包含：权重 SHA-256、制品签名和算法、提示词/嵌入/知识索引版本、适用范围、GPU 容量基线和回滚目标。模型状态只能按以下方向推进：

`DRAFT -> APPROVED -> FROZEN -> ROLLED_BACK/RETIRED`

`APPROVED` 的前置条件是：

1. 已脱敏、可复现的临床评测集和报告；
2. 假阴性（危险患者未升级）和错误分诊计数达到本院批准的阻断阈值；本项目默认两者均须为零，任何例外都必须有临床委员会书面批准；
3. 提示词注入、恶意附件、越权/PHI 外泄红队报告为 `PASSED`；
4. 已完成并记录可恢复的回滚演练（包括数据完整性检查和恢复时长）；
5. 至少一名独立审核者完成评测复核；申请人不能批准自己的变更。

冻结后禁止原地覆盖权重、提示词或索引。变更必须先在 `governance_changes` 创建请求，附验证证据和可执行回滚计划，经独立审批后执行；回滚演练也必须记录为变更并保留演练日志。

## 运行监测与 CAPA

按固定窗口写入 `model_monitoring_snapshots`：输入分布漂移指标及阈值、GPU 利用率/显存和队列延迟 P95、容量基线、异常处置。漂移或容量告警不会自动改变临床结论，而是触发人工复核、限流或冻结发布。

任何错误分诊、危险信号漏报、知识过期、越权访问或恶意附件绕过都要在 `safety_incidents` 登记。关闭事件前必须填写根因和纠正/预防措施（CAPA），并保留证据 URI。事故关闭不等于恢复上线；恢复仍需重新评测、审批和小流量验证。

## 发布前证据包

医院上线评审至少应能从数据库和制品库导出：模型制品签名与摘要、评测集脱敏证明、混淆矩阵/假阴性清单、红队报告、GPU 基线和压测报告、知识源登记及审核记录、变更/回滚演练记录、事故与 CAPA、审计日志和恢复演练结果。缺任何一项时，预检应保持失败，系统只能运行在非临床演示或受控试点模式。

后端控制面接口位于 `/api/governance/**`，由医院身份系统授予的角色控制；AI 服务仍只接收内部服务令牌。Redis 仅用于协调状态，不保存明文患者或评测样本，MySQL 是上述治理记录的权威存储。
